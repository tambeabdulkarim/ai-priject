# Production Secrets Checklist

**Created:** Phase 21 (Production Infrastructure Preparation), 2026-08-06 · **Read-only deliverable — no real secret values appear anywhere in this document.** Every "Where it is generated" / "Where it is stored" column describes a process the project owner must carry out directly, outside any AI session, per the security-hygiene principle established in Phase 19 and reaffirmed every phase since.

For the raw templates these secrets fill in, see `.env.production.example` (frontend/shared) and `.env.server.production.example` (backend) at the repository root.

| Secret | Purpose | Where It Is Generated | Where It Is Stored | Rotation Recommendation |
|---|---|---|---|---|
| `JWT_PRIVATE_KEY` | Signs access/refresh tokens (RS256) | Owner's own machine: `openssl genrsa -out private.pem 2048` | Hosting provider's environment-variable store (e.g., Railway/Vercel secrets), never in a file committed to git | Rotatable, but requires a coordinated rollout (old tokens signed with the previous key must be allowed to expire naturally, or all sessions invalidated) — recommend annually or immediately on suspected compromise |
| `JWT_PUBLIC_KEY` | Verifies tokens signed by `JWT_PRIVATE_KEY` | Derived from the same `openssl` step, same machine | Same as above | Rotate in lockstep with `JWT_PRIVATE_KEY` — they are a pair |
| `PASSWORD_PEPPER` | Server-side secret appended before Argon2id password hashing (the main Phoenix repository's `docs/10-SECURITY-BIBLE.md` §4) | Owner's own machine: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` | Hosting provider's environment-variable store | **Treat as immutable once set.** Rotating without a dual-pepper migration path (not currently implemented) breaks every existing user's password verification. If rotation is ever required, it must be scoped as its own engineering task first, not just an env-var change. |
| `MFA_ENCRYPTION_KEY` | AES-256-GCM key encrypting stored TOTP secrets at rest (the main Phoenix repository's `docs/10-SECURITY-BIBLE.md` §5) | Same generation command as `PASSWORD_PEPPER` | Hosting provider's environment-variable store | **Treat as immutable once set.** Rotating invalidates every enrolled user's stored TOTP secret, forcing re-enrollment — acceptable only as a deliberate, communicated security event, not routine hygiene. |
| `DATABASE_URL` | Production Postgres connection string | Neon (or chosen provider) dashboard, new dedicated production project | Hosting provider's environment-variable store | Rotate the password component periodically (provider-dependent — Neon supports password reset without downtime); never rotate by editing the string manually without confirming the provider's own reset flow |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | Production Redis (rate-limiting/session-adjacent state) | Upstash dashboard, new dedicated production database | Hosting provider's environment-variable store | Rotate the token via Upstash's dashboard if compromise is suspected; low-frequency rotation is acceptable otherwise (not a long-lived secret with high blast radius like the pepper/MFA key) |
| `STORAGE_ENDPOINT` / `STORAGE_BUCKET` / `STORAGE_ACCESS_KEY_ID` / `STORAGE_SECRET_ACCESS_KEY` / `STORAGE_REGION` | Production object storage (B2 or any S3-compatible provider) — course media, uploads | Backblaze B2 (or chosen provider) dashboard, new dedicated production bucket + application key | Hosting provider's environment-variable store | Rotate the access key periodically via the provider's dashboard (revoke old key only after confirming the new one works — avoid a storage outage from a bad rotation) |
| `STRIPE_SECRET_KEY` | Server-side Stripe API access — **must be a LIVE key**, not the test key used throughout development | Stripe dashboard, Live mode | Hosting provider's environment-variable store | Rotate immediately on suspected compromise (Stripe supports instant key revocation); otherwise low-frequency is acceptable |
| `STRIPE_WEBHOOK_SECRET` | Verifies incoming Stripe webhook signatures | Stripe dashboard, created *after* the backend has a real, stable public URL to register the webhook against | Hosting provider's environment-variable store | Rotates automatically if the webhook endpoint is ever recreated; otherwise stable |
| `POSTMARK_API_KEY` | Sends transactional email (verification, password reset, MFA notifications) via `EmailService` | Postmark dashboard, "API Tokens" tab, production server | Hosting provider's environment-variable store | Rotate on suspected compromise; Postmark supports issuing a new token without downtime if the old one is revoked after the new one is deployed |
| `EMAIL_FROM_ADDRESS` | Verified sending address | Must correspond to a domain verified in Postmark (DNS records: DKIM/Return-Path) | Hosting provider's environment-variable store (not a secret in the traditional sense, but must stay consistent with DNS records) | Not typically rotated — changing it requires re-verifying a new domain/address in Postmark first |
| `AI_PROVIDER_OPENAI_API_KEY` / `AI_PROVIDER_ANTHROPIC_API_KEY` | AI Gateway calls (optional — only required if AI is in launch scope) | OpenAI dashboard / Anthropic Console | Hosting provider's environment-variable store | Rotate on suspected compromise or unexpected usage spikes; both providers support instant key revocation |
| `NEXT_PUBLIC_SITE_URL` / `NEXT_PUBLIC_API_URL` | Public-facing URLs baked into the frontend build | The chosen production domain, once DNS is live | Hosting provider's environment-variable store (not secret — publicly visible in the built frontend regardless) | Not a rotation candidate — changes only when the domain itself changes |

## Notes on "session secrets"

Phoenix does not use a separate server-side session-secret value distinct from the JWT keypair — authentication is stateless (RS256 JWT), and session-adjacent state (refresh tokens, rate-limit counters) lives in the database and Redis respectively, not in a cookie-signing secret. If a future feature introduces cookie-based session signing, add its secret to this table at that time — do not invent one now that the current architecture doesn't use.

## General storage guidance

For an initial production launch, storing every secret above in the chosen hosting provider's built-in environment-variable store (Railway/Vercel/Render, etc.) is an acceptable, secure baseline — all of the major providers encrypt these at rest and restrict access to project collaborators. A dedicated secrets manager (AWS KMS, HashiCorp Vault) is a reasonable upgrade once team size or compliance requirements justify the added operational complexity (see the main Phoenix repository's `docs/phase21-v1.1-roadmap.md` Section 4) — not required to launch.
