## 1. Frontend Architecture Report (Summary)

The backend (`apps/api`) exposes a single versioned REST surface (`/api/v1/...`) across 19 documented resource groups (Auth, Users, Profiles, Courses, Lessons, Enrollments, Progress, Certificates, Library, Marketplace, Orders, Payments, Files, Media, AI, News, Notifications, Administration, Settings), all sharing four platform-wide standards: cursor pagination, a fixed error envelope, JWT-bearer auth with an httpOnly-cookie refresh flow, and RBAC enforced server-side (UI-side permission checks are a UX convenience only, never the security boundary — `docs/09` §5).

The existing monorepo scaffold already matches `docs/09` §1 exactly: `apps/web`, `apps/admin`, `packages/api-client`, `packages/types`, `packages/validation`, `packages/ui`, `packages/i18n`, `packages/config` all exist as empty/near-empty scaffolds. This phase's job is to design what goes inside `packages/api-client`, `packages/types`, `packages/validation`, and the `apps/web` integration layer (`services/`, `hooks/`, `providers/`, etc.) — before any page is built, so every subsequent page consumes the same typed, tested integration layer instead of each feature reinventing fetch/auth/error-handling logic.

Key architectural decisions this phase locks in (all traceable to `docs/09`/`docs/16`, none invented):

| Decision | Choice | Why |
|---|---|---|
| HTTP client | Native `fetch`, not axios | Next.js 14 App Router extends `fetch` with its own caching/revalidation integration; the backend itself already standardizes on native `fetch` (`RedisService`, `BreachedPasswordService`) — no reason to add a dependency for a capability the runtime already provides. |
| Server state | TanStack Query | `docs/09` §8, explicit. |
| Client UI state | `useState`/`useReducer` locally, Zustand for cross-component client state | `docs/09` §8, explicit. |
| Forms | React Hook Form + `packages/validation` (zod) | `docs/09` §8, explicit — the same zod schema shape informs (but does not replace) the backend's own class-validator DTOs, since the two are independent implementations of the same documented validation rules, not a shared runtime import across the Node/Nest boundary. |
| Auth token storage | Access token in memory only; refresh token in httpOnly cookie | `docs/16` "Authentication Flow" + `docs/10-SECURITY-BIBLE.md` — refresh token is "never accessible to client-side script." |
| Type source | Hand-authored in `packages/types`, mirroring `docs/16` response shapes | No OpenAPI generator exists in the backend yet (`docs/09` §6 recommends contract-first OpenAPI generation as a future step, not present today) — noted as a **BLOCKED BY DOCUMENTATION / not-yet-built** item, see §2.11. |

## 2. API Layer Design

### 2.1 Layering overview

```
packages/types/          → Pure TS types/interfaces mirroring docs/16 request & response bodies. Zero runtime code, zero dependencies.
packages/validation/     → zod schemas per DTO, shared shape-reference with apps/api's class-validator DTOs (independently maintained, same documented rules).
packages/api-client/     → Framework-agnostic typed SDK: one function per documented endpoint. No React. No Next.js. Usable from apps/web, apps/admin, future apps/mobile.
apps/web/src/services/   → Thin, app-specific composition over packages/api-client (e.g. wiring the access-token getter, the 401-refresh interceptor) — NOT a second copy of the client.
apps/web/src/hooks/      → TanStack Query hooks (useCourse, useEnrollments, ...) built on services/. This is what feature components actually import.
```

Rule (mirrors `docs/09` §3's "primitives never import features" rule): `packages/api-client` never imports React, Next.js, or anything app-specific. `apps/web/src/hooks` never calls `fetch` directly — always through `services/`.

### 2.2 API Client (`packages/api-client`)

- One typed function per documented endpoint, grouped by resource (`auth.login()`, `courses.list()`, `courses.getBySlug()`, `enrollments.refund()`, ...), generated by hand from `docs/16` (see §2.11 for the future-automation note).
- Every function signature: `(params, requestOptions?) => Promise<ApiResult<T>>` — never throws for a documented error response; throwing is reserved for genuine transport failures (network down, timeout). Documented 4xx/5xx responses are returned as a typed `ApiError` value (see §2.5), so callers branch on `error.code` per `docs/16`'s Error Response Standard without try/catch sprawl.
- The client itself is **stateless and injectable**: it accepts a `ClientConfig` (base URL, a `getAccessToken()` callback, a `onUnauthorized()` callback) at construction time rather than reading global state — this is what lets `apps/web`, `apps/admin`, and a future `apps/mobile` each supply their own token storage/refresh strategy without forking the client.

### 2.3 Authentication Client (`packages/api-client/auth`)

Wraps exactly the endpoints in `docs/16` §1 (Authentication) and §2 (`/users/me/change-password`):
`register`, `verifyEmail`, `login`, `refresh`, `logout`, `logoutAll` (mirrors `revokeAllForUser`/`revokeAllForUserExcept` built in the backend — see `docs/16` Authentication Flow step 4), `forgotPassword`, `resetPassword`, `changePassword`.

Distinguished from the generic API client only in that it's the one place allowed to mutate the in-memory access-token cell and trigger the refresh-cookie flow — every other resource client depends on it, never reimplements it.

### 2.4 Refresh Token Flow

Mirrors `docs/16` "Authentication Flow" (steps 2–4) and the backend's actual implementation (`RefreshTokensService.rotate`, reuse-detection → full session-family revocation) exactly:

1. Access token lives in an in-memory module-level variable inside `apps/web/src/services/auth-client.ts` — **never** `localStorage`/`sessionStorage` (XSS-exfiltratable) and never a client-readable cookie.
2. Refresh token is an httpOnly, `Secure`, `SameSite=Lax` cookie, set by the backend's `Set-Cookie` response header on login/refresh — the frontend never reads or stores it directly; the browser attaches it automatically to `credentials: 'include'` requests to the API origin.
3. A single-flight guard (`refreshPromise: Promise<string> | null` module-level variable) wraps the refresh call so N concurrent 401s trigger exactly one `/auth/refresh` call, not N — every other caller awaits the same in-flight promise.
4. On refresh success: update the in-memory access token, retry the original request(s) once.
5. On refresh failure (expired/revoked/reuse-detected — backend returns 401): clear in-memory state, call `onUnauthorized()` (see §4.9), redirect to `/[lang]/login?redirect=<original-path>`. Never silently retry a second time — one refresh attempt per failed request, per `docs/16`'s explicit reuse-detection semantics (a second failure means the session is genuinely gone, not flaky).
6. `logoutAll` (mirrors the backend's session-revocation-except-current logic added during the production-readiness pass) invalidates every *other* session; the acting session's own access token remains valid until its natural 15-minute expiry, matching the backend's actual behavior (`changePassword`'s "revokes other sessions" pattern, generalized).

### 2.5 Fetch Wrapper & Error Handling

A single low-level `request<T>()` function in `packages/api-client/core/request.ts` that every endpoint function calls:

- Builds the request (`Authorization: Bearer <token>` when present, `credentials: 'include'` always, JSON body serialization with `snake_case` conversion — see §2.6).
- Parses the response body once; on non-2xx, maps the documented envelope (`docs/16` "Error Response Standard": `error.code`, `error.message`, `error.details`, `error.request_id`) into a typed `ApiError` object — **never** re-throws a generic `Error` for a documented failure, so `error.code` stays branchable (`if (result.error?.code === 'VALIDATION_ERROR')`) all the way up to the UI layer without string-matching.
- On a 401 whose body isn't itself from `/auth/refresh` or `/auth/login`, transparently triggers the refresh flow (§2.4) and retries once before surfacing the error.
- On a genuine network/transport failure (no HTTP response at all — offline, DNS failure, timeout), throws a distinct `NetworkError` — this is the one case callers should `try/catch`, since it has no `error.code` to branch on.

### 2.6 Response Typing

- `packages/types` defines the response shape **exactly** as documented in `docs/16` — e.g. `CourseSummary`, `CourseDetail`, `PaginatedResponse<T>` (`{ items: T[]; next_cursor: string | null; total_count?: number }` per the Pagination Standard).
- Field casing: the wire format is `snake_case` (`docs/16` API Naming Standards, matching the DB column convention). `packages/api-client`'s `request()` wrapper performs a single, generic recursive `snake_case → camelCase` conversion on every response (and the reverse on every request body) at the transport boundary — so `packages/types` and every consumer above it works in idiomatic camelCase, and the wire-format detail is contained in exactly one place, not repeated per endpoint.
- No `any`. Every endpoint function's return type is the specific documented shape; unions are used for endpoints with a documented BLOCKED/`NotImplementedException` path (e.g. `PATCH /notifications/preferences`, which the backend deliberately 501s — the client types this as a call that always resolves to an `ApiError` with `code: 'NOT_IMPLEMENTED'`, not hidden or omitted from the client surface, so the UI can show an honest "not available yet" state rather than a broken button).

### 2.7 Pagination Helpers

- `packages/api-client/core/pagination.ts` exports a generic `createCursorPaginator<T>(fetchPage)` used by every list endpoint's TanStack Query hook via `useInfiniteQuery` — `getNextPageParam: (lastPage) => lastPage.next_cursor ?? undefined`, matching the documented envelope exactly (§2.6).
- `limit` defaults to 20 client-side too (matching the documented server default), capped at 100 client-side before the request is even sent (fast feedback; the server still clamps independently per `docs/16`, defense in depth, not a trust boundary shift).

### 2.8 Query Helpers (TanStack Query)

- `apps/web/src/hooks/` — one hook file per resource (`useCourses.ts`, `useEnrollments.ts`, ...), each a thin wrapper: `useQuery`/`useInfiniteQuery`/`useMutation` calling into `services/`, with query keys defined in one central `queryKeys.ts` (e.g. `['courses', 'list', filters]`, `['courses', 'detail', slug]`) so cache invalidation after a mutation (`useMutation({ onSuccess: () => queryClient.invalidateQueries(['courses','list']) })`) is consistent and greppable platform-wide, never an ad hoc string per component.
- Mutation hooks that map to a documented `Idempotency-Key`-eligible endpoint (`docs/16` Idempotency Rules: order creation, payment-adjacent actions) generate and attach a UUIDv4 idempotency key **once per mutation attempt** (stored in the mutation's local closure, regenerated only on a genuinely new user-initiated submission, not on TanStack Query's own automatic retry) — this is what makes retrying a flaky checkout safe.

### 2.9 Upload Helpers

Mirrors the backend's actual, verified two-step flow (`docs/16` §13, `FilesService.requestUploadUrl`/`completeUpload`) exactly — **not** a naive multipart POST to the API:

1. `uploadHelpers.uploadFile(file, onProgress?)` calls `POST /files/upload-url` to get a presigned URL + `upload_id`.
2. Uploads the raw file directly to the presigned URL (browser → object storage, never through the Next.js server or the API server — `docs/09` §9) via `fetch` with a `ReadableStream` body where supported, falling back to `XMLHttpRequest` for real upload-progress events (native `fetch` still has no cross-browser upload-progress API as of this writing — `XMLHttpRequest` is the pragmatic, documented-compatible exception to the "no axios" rule, kept isolated to this one helper).
3. Calls `POST /files/:uploadId/complete` to finalize.
4. Returns the created `File` record (`scan_status: 'pending'`, per the backend's real, unfaked malware-scan-pending state) — the UI must show a "processing" state, not assume immediate availability, matching actual backend behavior rather than an idealized instant-success flow.

### 2.10 Download Helpers

Every download path in the real backend resolves a **signed URL from a specific, already-entitlement-gated endpoint** — `GET /files/:id`, `GET /media/:id`, `GET /certificates/:id`, `POST /library/items/:id/access` — never a raw storage URL. `downloadHelpers.getSignedUrl(kind, id)` dispatches to the correct one of these four by content kind (a discriminated union in `packages/types`, mirroring the exact dispatch the backend's `FilesRepository.findEntitlementContext` performs server-side per the production-readiness fix) and surfaces the documented 425 ("still scanning"/"still processing") as a distinct, UI-representable state — not an error to swallow, a real "come back shortly" status the backend actually returns.

### 2.11 Permission Helpers

- `packages/api-client` never makes an authorization *decision* — that's the backend's job (`docs/09` §5: UI checks are "never the security boundary"). It only exposes **what the current user's token claims**: `hasRole(role)`, `hasAnyRole(roles[])`, read from the decoded (not re-verified — signature verification is meaningless client-side) JWT payload's `roles` claim, cached in the auth context (§5).
- A `<RequireRole roles={[...]}>` component and a `useHasRole()` hook (in `apps/web/src/guards/`) consume this purely for **hiding/disabling UI affordances** the user's role wouldn't be allowed to use anyway — e.g. hiding the "Publish" button from a `learner`. The actual `403` the backend would return if they tried anyway remains the real enforcement; the helper only prevents a confusing round-trip for the common case.
- **BLOCKED BY DOCUMENTATION (partial):** fine-grained `resource:action` permission checks (e.g. "can THIS user edit THIS specific course," which depends on ownership, not just role) cannot be fully resolved client-side without an extra API call, since ownership isn't in the JWT. The permission helper exposes role-level checks only; per-resource ownership checks are deferred to the data already returned by the resource's own `GET` (e.g. `course.instructor_id === currentUser.id`), computed in the feature hook, not invented as a new client-side authority.
- **Not-yet-built, noted honestly rather than assumed:** `docs/09` §6 recommends contract-first OpenAPI generation for `packages/api-client`; no OpenAPI spec exists in `apps/api` today (it's hand-written NestJS controllers/DTOs, not `@nestjs/swagger`-annotated). This phase's client is therefore **hand-authored against `docs/16` + the actual DTOs**, kept in sync manually. Automating this is a legitimate future improvement, not something to fake now.

### 2.12 Caching Strategy

| Data | Strategy |
|---|---|
| Public, rarely-changing (published courses/news/library/marketplace listings, `GET /settings/public`) | TanStack Query `staleTime: 5min`, Next.js Route/Server-Component fetch with `revalidate` tags where SSR'd (`docs/09` §14: "revalidate on publish via webhook" — noted as a future ISR-webhook wiring, not built this phase). |
| User-specific, changes on the user's own actions (`/users/me`, `/enrollments/me`, `/notifications/me`) | TanStack Query `staleTime: 0`, refetch-on-window-focus on, invalidated explicitly by the mutation that changed it — never time-based alone. |
| Admin analytics (`GET /admin/analytics/overview`) | `staleTime: 1min`, manual refresh button — matches the backend's own "not real-time, read-replica-style" framing even though no replica is actually provisioned yet (documented infra gap, inherited as-is). |
| Access token | In-memory only, never cached across page reloads by design (§2.4) — a hard reload always re-derives it via the refresh cookie, which is the intended security property, not a gap to "fix" with persistence. |

### 2.13 Retry Policy

- TanStack Query default: 3 retries with exponential backoff for `GET`s that fail with a network error or a `5xx`. **Never** auto-retry a `4xx` (per `docs/16`'s Error Response Standard, a 4xx is a client-correctable condition, not a transient fault — retrying it identically wastes a request against per-account rate limits documented in `docs/16` "Rate Limiting Strategy").
- Mutations: **no automatic retry** by default (`retry: false` on `useMutation`) except where the endpoint is documented `Idempotency-Key`-eligible (§2.8) — an accidental double-submit on a non-idempotent endpoint (e.g. `POST /library/items/:id/bookmark`, which is itself idempotent-by-design per `docs/16`, vs. `POST /orders`, which needs the explicit key) must never silently duplicate a side effect.
- A `429` response's `Retry-After` header (documented, present on every rate-limited response) is honored directly — the client schedules its retry at that exact delay, not a generic backoff guess.

### 2.14 Timeout Policy

- Default request timeout: 15s for standard reads/writes, 60s for the upload-URL and AI-request endpoints specifically (`docs/16` §15 AI: response times are provider-dependent and explicitly out of the client's control), implemented via `AbortController` passed into `fetch` — never a bare unbounded `fetch`.
- A timed-out request surfaces as the same `NetworkError` as an offline failure (§2.5) — from the UI's perspective both are "couldn't complete, offer retry," and conflating them is intentional simplicity, not an oversight.

## 4. Authentication Lifecycle

Every step below is checked against the actual backend behavior (`apps/api/src/modules/auth/`, `docs/16` §1), not an idealized flow.

### 4.1 Login
`POST /auth/login` → access token (body) + refresh token (`Set-Cookie`, httpOnly). Store access token in memory (§2.4). Decode JWT claims (`roles`, `sessionId`) into `AuthContext` — never re-fetch `/users/me` just to get roles the token already carries, but **do** fetch `/users/me` once for full profile data (email, locale, etc. — not in the JWT per `docs/10-SECURITY-BIBLE.md` §7's minimal-claims policy).

### 4.2 Register
`POST /auth/register` → always returns `verification_required: true` shape (enumeration-safe per `docs/16`, identical response whether or not the email already existed) — the UI must show the same "check your email" state unconditionally, never branch on whether registration "actually" succeeded, or it defeats the backend's own enumeration protection.

### 4.3 Refresh
Automatic, transparent, triggered only by a 401 (§2.4) — never a proactive timer-based refresh, since the access token's exact expiry isn't something the client should independently track (matches the backend's actual "no refresh-ahead" design).

### 4.4 Logout
`POST /auth/logout` (revokes current session) → clear in-memory token, clear `AuthContext`, redirect to `/[lang]`. The refresh cookie is cleared server-side via the logout response's own `Set-Cookie` (expired cookie), not client-side `document.cookie` manipulation (can't — it's httpOnly).

### 4.5 Logout All
Maps to the backend's session-revocation-except/all pattern — UI-level "Log out of all devices" in account settings. Per the backend's actual `changePassword` behavior (production-readiness fix), changing password already does this implicitly for *other* sessions; a dedicated "Logout All" affordance additionally revokes the current session too, ending with a forced re-login (the more aggressive of the two, so UI copy must not conflate them).

### 4.6 Forgot Password / 4.7 Reset Password
`POST /auth/forgot-password` → always the generic "if this email exists..." response (enumeration-safe, matches backend exactly — see `docs/16`). `POST /auth/reset-password` with the emailed token → on success, per backend behavior, **all** existing sessions are revoked (not "other" — there's no "current" session mid-reset-flow), so the UI must send the user to `/login` after reset, not attempt to keep them signed in.

**BLOCKED BY DOCUMENTATION:** the reset/verification email is never actually delivered by the backend today (no email provider configured — `docs/archive/backend-build-handoff/SESSION-HANDOFF.md`, `AuthService`'s own logged-not-sent tokens). The frontend flow is fully buildable and correct, but end-to-end manual testing of it will require reading the token from server logs, not an inbox, until that infra gap is closed. This is a pre-existing, already-disclosed backend limitation, not a frontend design gap.

### 4.8 Protected Routes
Two layers, matching `docs/09` §5's "two enforcement layers" principle:
1. **Edge (Next.js `middleware.ts`):** cheap, cookie-presence-only check (refresh cookie exists → assume "maybe authenticated," let the request through to the route; absent → redirect to `/login` immediately for routes under the `(app)`/`(checkout)` route groups). This is a UX fast-path, not a security boundary — middleware never decodes/verifies the JWT.
2. **Route/Component (`RequireAuth`, `useAuth`):** the real check — if `AuthContext` has no valid user after hydration (including a failed silent-refresh attempt), redirect client-side. The actual authorization for every data fetch still happens server-side on `apps/api` regardless of what the frontend believes.

### 4.9 Role Guards / 4.10 Permission Guards
`RequireRole`/`useHasRole` (§2.11) gate route-group-level UI (e.g. the entire `/instructor` route group checks `hasAnyRole(['instructor','content_editor','admin','superadmin'])`). Fine-grained ownership guards (e.g. "only *this* course's instructor sees the edit button) are computed per-resource in the feature hook from already-fetched data, not a separate guard abstraction — there's no client-side ownership data to guard on until the resource is fetched anyway.

### 4.11 Session Recovery
On app load / hard refresh: `AuthProvider` attempts one silent `POST /auth/refresh` (relying on the httpOnly cookie) before rendering any authenticated UI. Success → populate `AuthContext` from the new access token. Failure → render as anonymous; no error shown (a logged-out user hitting a public page is the expected, common case, not a fault).

### 4.12 401 Recovery
Handled entirely inside the fetch wrapper (§2.5/§2.4) — by the time a 401 reaches a component/hook, it has already survived one silent refresh-and-retry attempt and genuinely means "not authenticated." Components never implement their own 401 handling.

### 4.13 403 Handling
Distinct from 401 by design (`docs/16` Error Response Standard: "authenticated but not authorized"). Surfaced as a typed `ApiError` with `code` reflecting the specific denial where the backend provides one (e.g. `FORBIDDEN`) — UI renders an in-context "you don't have access to this" state, **not** a redirect to login (the user *is* logged in; redirecting them to log in again is confusing and wrong). For admin-area 403s specifically, redirect to a dedicated `/[lang]/403` page rather than an inline message, since an admin route reached without the role at all (not just a specific action) indicates a stale/incorrect navigation state worth a full page.

## 5. Global State Architecture

Precise placement per `docs/09` §8, applied to every concrete piece of state this phase's API layer produces:

### Belongs in Context (`AuthContext`, via `AuthProvider` — the **only** app-wide React Context this phase defines)
- Current user's decoded JWT claims (`sub`, `roles`, `sessionId`).
- Current user's profile object (from `GET /users/me`), refetched on invalidation, not polled.
- Auth status enum: `'loading' | 'authenticated' | 'anonymous'`.
- *Why Context and not Zustand:* this is genuinely global, read by nearly every component tree (route guards, nav, permission checks), changes rarely, and its "provider wraps the whole app once" shape is exactly what Context is for — using Zustand here would just be Context with extra ceremony.

### Belongs in React Query (TanStack Query cache — **not** Context, **not** Zustand)
- Every server-owned resource: course lists/details, enrollments, progress, certificates, library items, marketplace products, orders, payments, notifications, admin data, settings.
- Rationale directly from `docs/09` §8: "the API is the source of truth, not client state" — none of this data has a meaningful client-only existence; duplicating it into Context/Zustand would just be a second, driftable cache next to TanStack Query's already-correct one.

### Belongs in local component state (`useState`/`useReducer`)
- Form field values before submission (owned by React Hook Form, which is itself local state under the hood).
- Modal/drawer open-closed, active tab, hover/focus UI state, in-progress upload percentage (§2.9) for a single upload widget.
- Anything that dies with the component and no sibling/ancestor needs to observe it.

### Belongs in Zustand (cross-component client-only state — used sparingly, only where Context/local state genuinely doesn't fit)
- Cart/checkout draft state before an order is actually created server-side (`docs/16` §11: an `Order` is a server resource once created, but the *drafting* of one — items added, coupon code typed — is client-only until `POST /orders` fires).
- Global UI chrome not worth a Context (e.g. mobile nav drawer open state, if shared between the header and an overlay that aren't in the same component subtree).
- **Deliberately not used for:** anything React Query already owns (would create two sources of truth), or anything only one component tree needs (just local state).

### Belongs in cookies
- The refresh token — httpOnly, set/cleared exclusively by the backend's `Set-Cookie` header, never written by frontend JS (§2.4). This is the **only** thing that belongs in a cookie; no other app state is cookie-stored.
- A locale preference cookie (`NEXT_LOCALE` or equivalent) for `docs/09` §2's `/[lang]/...` routing to persist across visits without requiring login — genuinely needs to survive a full page reload before any JS runs, which only a cookie (read by the Next.js routing layer itself) achieves.

### Belongs in memory only (never persisted, gone on hard refresh)
- The access token itself (§2.4 — this is the security-critical one; persisting it anywhere durable defeats the short-lived-JWT design).
- The single-flight refresh promise (§2.4).
- Idempotency keys in flight (§2.8) — regenerated per genuine new submission, never reused across a page reload.

Follows `docs/09` §2's route-group shape exactly; the list below is every page implied by an actual, documented, implemented backend capability — no page is listed for a BLOCKED-BY-DOCUMENTATION backend feature (e.g. no OAuth-login page, since `oauthCallback` is `NotImplementedException` in the real backend; no MFA-setup page, for the same reason).

## 8. Parallel Development Roadmap

Ordered to unblock maximum parallelism while respecting real dependencies (a hook can't be built before its types exist; a page can't be built before its hooks exist).

### Wave 0 — Sequential prerequisite (blocks everything else, keep it short)
1. `packages/types` — all resource types (§3). No dependencies. **Must land first** since every other package imports it.
2. `packages/config` env schema, `apps/web/src/config/env.ts`.

### Wave 1 — Fully parallel, zero merge-conflict risk (each owns disjoint files)
Once Wave 0 lands, these can be built simultaneously by different people/agents with no shared-file contention:
- **Track A:** `packages/validation` schemas (mirrors `packages/types` 1:1, no cross-track dependency beyond Wave 0).
- **Track B:** `packages/api-client/core/*` (request wrapper, pagination, case-convert, client-config — §2.5/2.6/2.7) — the foundational plumbing every resource client needs, so this track should be prioritized to finish first within Wave 1 if any sequencing is needed at all.
- **Track C:** `packages/ui/primitives` (§7) — zero dependency on API layer at all, can start immediately in parallel with Wave 0 even.
- **Track D:** `apps/web/src/middlewares/middleware.ts`, `apps/web/src/constants/routes.ts` — route-shape work, independent of the API client's internals.

### Wave 2 — Parallel by resource group (depends on Wave 1 Track B landing)
Each resource group's `api-client` module + its `hooks/` file + its `packages/ui` domain components is one self-contained, independently assignable unit — these can all proceed simultaneously since they touch entirely disjoint files:
- Auth + Users + Profiles (one track — tightly coupled, §4's whole lifecycle)
- Courses + Lessons + Enrollments + Progress + Certificates (one track — the learning domain)
- Library
- Marketplace + Orders + Payments
- Files + Media (depends on nothing from the other tracks beyond Wave 1)
- AI
- News
- Notifications
- Admin + Settings

Nine independently parallelizable tracks. Merge-conflict risk is near-zero because each track's files (`packages/api-client/<resource>.ts`, `apps/web/src/hooks/use<Resource>.ts`) never overlap with another track's, **except** `packages/api-client/src/index.ts` and `apps/web/src/hooks/queryKeys.ts`, which every track appends an export line to — mitigate by having each track add its exports as a separate, small, easily-auto-mergeable diff at the end of a stable-ordered list (alphabetical by resource name), not by editing near another track's recently-added line.

### Wave 3 — Sequential per page, but pages themselves parallelize once Wave 2's relevant track lands
`AuthProvider`/`QueryProvider`/`AppProviders` (§3) must land before any page can be built (every page needs the query client + auth context mounted), but is a single small, fast task — not a bottleneck. After that, page-building parallelizes exactly along the same resource-group lines as Wave 2, since a page only needs its own resource group's hooks, not all of them.

### Explicit non-parallel dependency chain (the only true bottleneck)
`packages/types` → `packages/api-client/core` → (any resource's `api-client` module) → (that resource's `hooks/`) → (that resource's pages). Everything else is parallel. This chain is short and front-loaded — once through it, the remaining ~90% of the work is the nine-track parallel wave above.

## Open BLOCKED BY DOCUMENTATION items (frontend-relevant, inherited from the backend)

These constrain what pages/flows can be *fully* built, not the architecture itself — noted here so Wave 2/3 implementers don't discover them mid-build and guess a workaround:

- OAuth login, MFA setup/challenge, notification-preferences UI: backend endpoints are `NotImplementedException` — no page should be built for these until the backend gap closes.
- Email/reset-link delivery: backend logs tokens instead of emailing them — any "check your email" flow works end-to-end only via server log inspection until an email provider is configured.
- `GET /admin/analytics/overview`'s DAU/MAU/read-replica framing: works correctly against the primary DB (documented gap, not a frontend concern) — no UI change needed, just don't assume replica-level query volume headroom.
